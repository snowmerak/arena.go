# 저장소 확장 가이드

현재 공개 생성자 `New(capacity)`는 기존과 같은 바이트 아레나를 만든다.
확장 준비는 라이브러리 내부 경계에 적용되어 있다. 사용자 코드가 임의의 unsafe
저장소를 등록하는 공개 플러그인 API나 pointerful allocator를 추가한 것은 아니다.

## 구현 위치

| 파일 | 책임 |
| --- | --- |
| `arena.go` | 제네릭 API, 할당 세대, 정확한 타입/시작 주소 검증, 수명 관리 |
| `slice.go` | 일괄 할당, 전체 슬라이스 검증, 배치 핸들 추출 |
| `backend.go` | 저장소 계약, 요청 정보, 실제 포인터와 구간 위치 |
| `byte_backend.go` | 바이트 저장소의 공간 배치, 재사용, 정렬, 물리 영역 검사 |
| `typeinfo.go` | 포인터 포함 여부의 재귀 검사와 캐시 |
| `checker.go` | 저장소에 공통인 핸들/타입 검사와 진단 API |
| `backend_test.go` | 독립된 typed heap 슬롯을 쓰는 두 번째 저장소로 연결 검증 |

호출 경로는 `Alloc[T] → allocationRequest → backend.allocate → 공통 할당 등록`이다.
제네릭 메서드는 계속 `Arena`에 둔다. 저장소 계약에는 크기, 정렬, 할당 종류,
정확한 `reflect.Type`을 전달하므로 저장소가 자신에게 맞는 할당 방법을 선택할 수 있다.
기본 저장소의 포인터 거부 정책은 `byteBackend`가 담당한다.

`AllocSlice[T](n)`은 `sliceAllocation` 종류와 정확한 `[n]T` 타입을 전달한다.
배열 전체가 하나의 할당이며 크기와 정렬은 배열 타입을 따른다. `typ`이 nil이 아닌
요청은 객체와 슬라이스 모두 typed 저장소를 사용해야 한다. 테스트용 heapBackend는
`reflect.New(request.typ)`으로 배열을 만들고 `SetZero`로 전체 참조를 지운다.
크기가 0인 배치도 고유 주소를 위한 최소 한 바이트를 확보한다.
슬라이스의 길이/용량, 원소 타입, 시작 주소는 공통 Arena 계층에서 검증한다.

## 새 저장소를 추가하는 순서

1. `backend` 인터페이스를 구현한다. 인스턴스는 한 Arena만 소유하고 모든 호출은
   Arena의 mutex 아래에서 직렬 실행된다. backend에서 Arena를 다시 호출하면 안 된다.
2. 공개 생성자가 옵션/용량을 검증한 뒤 내부 `newArena(storage)`로 조합한다.
   기본 `New`의 계약을 조용히 변경하지 않고 별도 생성자를 추가할 수 있다.
3. 여러 청크를 사용하면 각 청크에 고유한 segment ID를 부여한다. 같은 청크 내에는
   offset으로 위치를 구분한다. 살아 있는 블록은 위치와 주소가 모두 서로 달라야 한다.
4. `check`에서 그 저장소의 물리적인 배치와 공통 live map이 일치하는지 검증한다.
5. 생성자와 함께 저장소별 경계 조건, GC 수명, 재사용, 메모리 예산 테스트를 추가한다.

## 반드시 지켜야 할 계약

- `allocate` 성공 시 최소 `max(size, 1)`바이트를 정렬하고 초기화해서 반환한다.
  반환된 포인터는 해제 전까지 움직이지 않는다. 실패 시 저장소를 소비하지 않는다.
- 저장소를 유지하는 Go 참조를 보관한다. 포인터 포함 객체는 처음부터 GC가 타입을
  인식하는 메모리에 할당한다. 바이트를 캐스팅하는 것만으로는 이 계약을 충족하지 못한다.
- `release`에는 원래 요청의 타입 정보까지 전달된다. pointerful 저장소는 typed 대입이나
  typed clear로 참조를 제거한다. 바이트 view로 지우는 구현을 공유하지 않는다.
- `reset`은 슬롯을 재사용하기 전에 외부 Go 참조를 지운다. `close`는 슬롯을 정리하고
  저장소가 보유한 참조를 해제한다. 세 연산은 실패하지 않는 계약이다.
  실패 가능한 외부 리소스 저장소를 추가하려면 오류 전파/부분 실패 정책부터 확장해야 한다.
- `locate`는 포인터의 구간 위치를 반환한다. Arena는 이후 실제 할당 시작 주소인지,
  요청한 타입과 같은지 추가 확인한다. 핸들 해제는 owner·할당 ID·구간·offset 모두 확인한다.
- byte/string 요청만 원시 바이트 view로 접근한다. 객체 요청에는 타입 기반 접근을 사용한다.
- `stats`는 저장 공간만 집계하고, 활성 할당 수는 Arena가 채운다. 여러 구간의 Capacity,
  Used, Free, Head, FreeBlocks는 합산하고 LargestFreeBlock은 최댓값으로 보고한다.
  Head는 각 구간의 점유 prefix 길이의 합이며 서로 떨어진 영역을 연속 공간으로 세면 안 된다.
- `check`는 전달받은 live map을 읽기 전용으로 사용한다. 포인터와 위치의 일치,
  지원 타입, 범위/겹침, 빈 구간, 사용량을 검증한다. 공통 체커가 정상이어도
  저장소의 물리 배치가 정상인지는 backend가 검사해야 한다.

## 타입별 청크를 붙일 때

이 경계는 타입 정보를 `reflect.Type`으로 전달한다. 예를 들어 새 backend에서
`reflect.MakeSlice(reflect.SliceOf(request.typ), count, count)`로 실제 typed 배열을
만들고, `reflect.Value`를 보관해 수명을 유지할 수 있다. 반환 슬롯은 타입이 있는
배열의 원소 주소여야 하며, 해제는 해당 원소의 `SetZero` 같은 typed 연산을 사용한다.

이는 향후 구현 방향이지 현재 제공하는 청크 allocator는 아니다. 청크별 남는 공간,
타입별 풀의 개수, 최대 용량, OOM 시 동작을 새 생성자에서 명확히 정의해야 한다.
현재의 byteBackend를 함께 사용하는 복합 backend도 같은 경계 뒤에서 구성할 수 있다.

`backend_test.go`의 heapBackend는 연결 계약만 검증하는 네 슬롯짜리 테스트 구현이다.
일반 타입별 풀의 성능, 동시성, 완전한 GC 수명 검증을 대체하지 않는다.
실제 backend에는 별도 테스트가 필요하다.

## 호환성과 비용

현재의 `New`, `Alloc[T]`, `Free`, String/Buffer API와 기본 용량·재사용 정책은 유지한다.
포인터 포함 타입 지원은 추가하지 않았다. `Buffer.Segment()`는 새 진단용 접근자이며,
기본 저장소에서는 0을 반환한다. 목록은 segment와 offset 순서로 정렬한다.

Buffer에 숫자 segment 필드가 추가되어 64비트 환경의 Buffer와 String 크기는
각각 32바이트에서 40바이트로 늘었다. 할당 메타데이터와 저장소 호출 비용도 추가됐다.
이것은 소스 API 호환성을 유지하는 구조 변경이며, 바이너리 레이아웃이나 동일한 성능을
보장하는 변경은 아니다. 원시 포인터의 해제 후 접근과 ABA 한계는 여전히 적용된다.
